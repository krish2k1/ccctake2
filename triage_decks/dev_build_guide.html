01 / THE PROBLEM

Forget insurance. Here's what we're building.

Think Spotify "Discover Weekly" — but for claims handling.

Spotify picks which songs you might like, then for each pick decides which playlist to surface it on. We pick which services a claim needs, then for each service pick which vendor performs it best for this specific case.

A "claims adjuster" manages 150 active cases. For every case they decide:

DECISION 1

Which services to engage

Out of 36 possible services (nurse, lawyer, investigator, translator, etc.) — what does this case need right now?

DECISION 2

Which vendor to use

For each service, the company has 3–5 approved vendors (think: 4 different nursing companies). Pick the best fit for this case.

Today, both decisions are made from memory and habit. No comparison data. No learning from outcomes. The same case is handled three different ways by three different adjusters. We're building the recommendation engine.

02 / THE BUSINESS · IN 60 SECONDS

Workers' comp · the only domain knowledge you need

premium (annual fee). 2. A worker gets injured. The employer reports it to the carrier — this is the FNOL ("First Notice of Loss"). A new claim is born. 3. The carrier pays the worker's medical bills + a portion of their lost wages (called "indemnity") until they return to work. 4. To handle the claim well, the carrier engages external vendors: nurses to coordinate care, lawyers to defend disputed claims, investigators for fraud, translators, etc. 5. The carrier reports the claim's progress to the state regulator (a system called EDI). The regulator can audit anything. Carrier profit margin = premium received − (medical + indemnity + adjuster salaries + vendor fees + overhead) → Smarter vendor decisions and earlier service engagement directly improve the bottom line. That's what we're building.

  },

  severity_score: 0.68,         // 0–1, predicted ultimate severity
  litigation_propensity: 0.31,  // 0–1, P(attorney involved)

  // services we've already engaged on this claim
  engaged_services: [
    { service_id: "F1", vendor: "Verisma", since: "2026-04-13" },
    { service_id: "B1", vendor: "Mitchell", since: "2026-04-14" }
  ],

  // medical / treatment signals
  treatment_plan_complexity: "multi-provider",
  opioid_days: 9,            // days since first opioid Rx
  treating_provider: { npi: "...", watch_flag: false }
}

Where does it come from?

A separate system called the claims core owns it. (Real-world names: Guidewire ClaimCenter, Duck Creek, Origami, or an in-house system.) You don't build that. You consume events from it.

jurisdiction
= US state. Each state has different WC laws. Your code must respect this.
venue
= the local court area where any lawsuit would be heard. Matters for picking lawyers.
reserve
= the carrier's running estimate of what this claim will ultimately cost. Updated as the claim develops.
indemnity
= wage replacement payments to the injured worker. Different from medical payments.
modified duty
= can the employer give the worker easier work while they recover? Big factor in cost.
catastrophic_flag
= severe injury (TBI, paralysis, amputation, ≥3rd-degree burn ≥30% body, fatality, multi-trauma).

06 / FOUR COMPONENTS · ONE SYSTEM

Break the black box into four services. Each one independently deployable.

C1

Service Identifier

Job: "What does this claim need?"

Input: a claim snapshot. Output: a list of services that should be engaged + when + why.

Tech: rules engine + ML classifier + timing model

C2

Vendor Pool + Scorecard

Job: "For this service, who's best?"

Input: a service + a claim context. Output: top-3 vendors with scores & rationale.

Tech: Postgres + scoring math + cache

C3

Composer

Job: "Bundle it for the adjuster, save it forever."

Calls C1, calls C2, applies governance rules, persists immutably, emits an event.

Tech: stateless orchestrator + append-only log

C4

Learning Loop

Job: "Watch what happened. Get smarter."

Refreshes vendor scores, retrains the classifier, mines override patterns, proves ROI.

Tech: batch pipeline + model registry · Phase 2

Mental model: C1 is like Spotify's recommender ("what should we suggest?"). C2 is like Yelp's ranking ("of these restaurants, which is best for the user?"). C3 is the UI assembler + audit ledger. C4 is the offline analytics that retrains everything.

Phase 1 (months 0–9): ship C1 + C2 + C3 with simple versions. Phase 2 (9–24): add C4 + sophisticated versions of C1/C2.

07 / COMPONENT 1 · SERVICE IDENTIFIER

"What does this claim need?" — three lanes, one output

There are 36 services in the catalog (see SERVICE_CATALOG.md). Each service is typed by how the decision gets made:

DET — deterministic rule
Simple if-statement. e.g. "if claimant.language ≠ 'en' → engage interpreter (C5)". No ML.
PROB — ML classifier
Probabilistic. e.g. "Given this claim's features, P(needs defense counsel) = 0.62 → recommend". We use a multi-label model — one model, many outputs.
TIME — timing model
Decision is when, not whether. e.g. "engage the nurse now vs in 14 days?". Survival-style model.
HUMAN — approval required
Even if recommended, a human must approve before engagement. Only one service: surveillance (D2). Privacy + legal reasons.

Why hybrid? Some services are policy — they should always fire under defined conditions (interpreter, MSA, state filings). Building an ML model for those would be over-engineering. Others are genuinely judgment calls — that's where the classifier earns its place.

# Pseudocode — Service Identifier

def identify_services(snapshot: ClaimSnapshot) -> List[ServiceRec]:

    services = []

    # LANE A · deterministic rules
    for svc in catalog.services_by_type("DET"):
        if rules.matches(snapshot, svc.rule):
            services.append(ServiceRec(
                service_id=svc.id,
                confidence=1.0,
                when="now",
                why=rules.explanation(snapshot, svc.rule)
            ))

    # LANE B · multi-label classifier
    probs = classifier.predict_proba(snapshot)
    # probs = { "A1": 0.78, "A6": 0.32, "D1": 0.61, ... }
    for svc_id, p in probs.items():
        threshold = config.threshold_for(svc_id)
        if p >= threshold:
            services.append(ServiceRec(
                service_id=svc_id,
                confidence=p,
                why=shap_attribution(snapshot, svc_id)
            ))

    # LANE C · timing model
    for svc in services:
        if catalog.has_timing(svc.service_id):
            svc.when = timing.recommend_window(snapshot, svc.service_id)

    # LANE D · HUMAN flag
    for svc in services:
        if catalog.requires_approval(svc.service_id):
            svc.routing = "HUMAN_APPROVAL"

    return dedupe_and_resolve_deps(services)
08 / COMPONENT 2 · VENDOR POOL + SCORECARD

"For this service + this claim, give me top-3 vendors"

Two stages, in order

Stage 1 · FILTER (eligibility — binary) · 8 yes/no checks the vendor must pass:

  • 1. State licensure current
  • 2. E&O insurance at carrier limits
  • 3. HIPAA BAA signed
  • 4. Compliance attestations on file
  • 5. No active regulatory action
  • 6. SOC 2 Type II report
  • 7. Rate card filed (machine-readable)
  • 8. Capacity below 85% utilization

+ per-claim filter: jurisdiction match, no conflict of interest, not on this claim's exclusion list.

Stage 2 · SCORE (weighted composite):

score =
   0.40 * outcome   # did similar claims close well?
 + 0.25 * cost      # savings/fee or cost per file
 + 0.15 * speed     # SLA hit rate, cycle time
 + 0.10 * specialty # match for THIS claim's specifics
 + 0.05 * adj_sat   # adjuster post-engagement survey
 + 0.05 * compliance
# Pseudocode — Vendor Pool

def rank_vendors(service_id, claim) -> List[RankedVendor]:

    # 1. fetch all vendors that offer this service
    candidates = vendor_master.offering(service_id)

    # 2. apply 8 hard gates + per-claim filter
    eligible = [v for v in candidates
                if is_eligible(v, service_id, claim).ok]

    # 3. score each eligible vendor — PER CLAIM
    scored = []
    for v in eligible:
        base = scorecard.get(v.id, service_id, claim.jurisdiction)

        if base.n_closed < 30:
            # not enough data — flag but don't rank
            scored.append(RankedVendor(v, status="provisional"))
            continue

        # specialty_fit is per-CLAIM, not stored
        specialty = compute_specialty_fit(v, claim, service_id)
        # match on body_part, language, geography, venue

        composite = (
            0.40 * base.outcome +
            0.25 * base.cost +
            0.15 * base.speed +
            0.10 * specialty +
            0.05 * base.adj_sat +
            0.05 * base.compliance
        )
        scored.append(RankedVendor(v, score=composite, breakdown=...))

    # 4. sort, then apply governance overlay
    ranked = sorted(scored, key=lambda r: -r.score)
    ranked = apply_anti_concentration(ranked, service_id)
    ranked = apply_exploration_quota(ranked)

    return ranked[:3]
09 / COMPONENT 3 · COMPOSER

The orchestrator. Calls C1, calls C2, persists immutably, emits an event.

# Pseudocode — Composer (the heart of the system)

async def on_claim_event(event: ClaimEvent):

    # 1. snapshot the claim state RIGHT NOW
    #    + pin model versions so we can reproduce later
    snapshot = claim_store.snapshot(event.claim_id)
    versions = registry.current_versions()

    # 2. ask C1 what services are needed
    services = await service_identifier.identify(snapshot)

    # 3. for each service, ask C2 for top-3 vendors
    blocks = []
    for svc in services:
        ranked = await vendor_pool.rank(svc.service_id, snapshot)
        blocks.append(ServiceBlock(svc, ranked))

    # 4. apply governance overlay
    blocks = governance.apply(blocks, snapshot)
    #   - hold D2 surveillance for human approval
    #   - enforce anti-concentration cap (50% per vendor)
    #   - apply 5% exploration quota

    # 5. compose the Recommendation object
    rec = Recommendation(
        rec_id=uuid4(),
        claim_id=event.claim_id,
        issued_at=now(),
        predecessor=last_rec_for(event.claim_id),  # lineage!
        snapshot_ref=snapshot.id,
        model_versions=versions,
        weights=governance.current_weights(),
        service_recommendations=blocks
    )

    # 6. PERSIST IMMUTABLY — append-only ledger
    ledger.append(rec)

    # 7. emit downstream event for UX, audit, warehouse
    bus.publish("RecommendationIssued", rec.to_event())

API surface (HTTP/JSON)

POST /v1/recommendations/issue
   body: ClaimEvent
   → 202 { rec_id }     # async, event-driven

GET  /v1/recommendations/by-claim/:claim_id/latest
   → 200 Recommendation

GET  /v1/recommendations/:rec_id
   → 200 Recommendation  # immutable, same forever

POST /v1/recommendations/:rec_id/action
   body: AdjusterAction
   → 202 { action_id }   # adjuster accept/swap/reject

GET  /v1/recommendations/:rec_id/lineage
   → 200 [rec_id, ...]   # walk the predecessor chain

Critical invariant: Recommendations are immutable. You never update one. If the claim changes and the recommendation is stale, the Composer issues a new recommendation with predecessor = old_rec_id. That's the audit history.

Why so strict on immutability?
A state regulator can audit any claim five years later. "Why did you do X on Jan 14, 2026?" You must answer with the exact data and models that drove the decision at that moment. Mutation would destroy that.
10 / COMPONENT 4 · LEARNING LOOP

Phase 2. Briefly — so you know what's coming.

LOOP 1 · weekly

Vendor score refresh

Pull last-week's vendor outcomes. Recompute scores with propensity correction + time decay. Push to the scorecard cache.

LOOP 2 · quarterly

Classifier retrain

Pull last quarter's labeled outcomes. Retrain the multi-label model. Validate on holdout. Run bias tests. Promote via model registry.

LOOP 3 · monthly

Threshold calibration

Per service, plot ROI of engagement at the current trigger threshold. Tighten or loosen based on observed marginal value.

LOOP 4 · monthly

Override mining

Cluster adjuster overrides by feature. If a pattern emerges (e.g. Tampa adjusters always swap vendor X for Y on shoulder claims), surface as a feature-engineering ticket.

The 5% holdout trick. When the system goes live, randomly suppress recommendations on 5% of claims for 6 months. Compare outcomes on the 95% (treatment) vs 5% (control) — that's how we prove the layer saves money. Without this, the finance team will spend three years arguing whether it worked. Bake this in from day 1 of production rollout.

In dev terms: a daily batch (Airflow/Dagster/cron) reads from a warehouse (Snowflake/BigQuery/etc.), writes back to (a) the vendor scorecard cache and (b) the model registry. The "online" path (C1/C2/C3) consumes the latest cache + latest model version at inference time. Standard offline/online ML pattern.

14 / NFRs · IN DEV TERMS

What "good" looks like operationally

SPEED

P50 < 2s · P95 < 5s

From event arrival to persisted Recommendation. The adjuster is waiting — no spinners. Profile each component independently. Cache vendor scores aggressively (they refresh weekly).

IDEMPOTENT

Replay = same output

Same event + same snapshot + same model versions = identical Recommendation. Key persistence by deterministic hash so re-delivery dedupes.

IMMUTABLE

Append-only ledger

Never UPDATE a Recommendation row. New ones link to old via predecessor_rec_id. Walk the chain for full history.

AUDITABLE

5-year point-in-time replay

Snapshot, model versions, weights, scores, candidates, action, outcome — all persisted, all queryable. Regulators ask "why" years later. You must answer exactly.

PHI / HIPAA

Encrypt everything

TLS 1.3 in transit, AES-256 at rest. Vendor packets redact identifiers (claim_number is opaque). Access controls per role. Don't log PII.

JURISDICTION

Config, not code

State-specific eligibility, weights, consumer-notice copy → data tables, not if state == 'CA' branches. Hard-coded jurisdiction logic will rot.

OBSERVABILITY

Trace every event

One trace ID per inbound event, propagated through C1 → C2 → C3 → vendor API call. Latency per component. Use OpenTelemetry or equivalent.

DEPLOYABLE

Each component independent

C1/C2/C3/C4 deploy separately. Feature-flag new classifier versions. Shadow mode for promotions. Standard ML deployment hygiene.

ADOPTION TARGET

≥70% accept rate · end of Phase 2

Measured as AdjusterAccepted ÷ RecommendationIssued. It's a product KPI, not an individual adjuster KPI (year 1, per policy).

15 / STACK SUGGESTIONS

Defaults. Override based on what your org already runs.

EVENT BUS

Apache Kafka (or Kinesis / Pub/Sub)

You need durable, replayable streams. Avoid lightweight message queues (RabbitMQ, SQS) — replay-from-the-past is non-negotiable for an event-sourced system.

SERVICE RUNTIME

Python for C1 + C4 · pick your poison for C2 + C3

Python for ML-heavy services because the ML ecosystem is there. Go / Java / TypeScript / Kotlin all fine for the orchestrator and the vendor pool. Pick what your team ships fastest.

RELATIONAL DB

PostgreSQL

Vendor master, eligibility, capacity, scorecard cache, append-only recommendation ledger. Use partitioning for the ledger (by issue date).

OBJECT STORE

S3 / GCS / Azure Blob

Snapshots, feature-store backing, model artifacts, audit pack exports. Cheap, durable, lifecycle-policied.

FEATURE STORE

Feast (or roll a thin one)

Online features served <10ms for the classifier. Offline features for retraining. If your scale is small, a Redis + Postgres pattern is fine to start.

MODEL REGISTRY

MLflow

Version every model. The Composer pins model_versions on every recommendation — and that pin must resolve to a specific artifact forever.

BATCH / ORCHESTRATION

Airflow · Dagster · Prefect

Weekly score refresh, quarterly retrain, monthly threshold review, monthly override mining. Pick one and stick with it.

OBSERVABILITY

OpenTelemetry + your stack

Datadog · Grafana · Honeycomb · anything. Traces are the priority — you need to see one inbound event flow through 3 services.

Architectural style: event-driven for async paths; REST/JSON for synchronous request/response (the UX SDK calls Composer over HTTP). CQRS-style read models for the vendor scorecard (writes via batch, reads via cache).

We're a recommendation engine for claim handling.

Spotify's Discover Weekly — but the "items" are services and vendors, and a human accepts or overrides every one. That mental model is more correct than any insurance-textbook framing.

2

The adjuster always decides. We never auto-engage a vendor on judgment-call services.

DET services fire automatically (interpreter, state filings). PROB services are suggestions. Surveillance (D2) requires a named-human approval — non-negotiable, regardless of model confidence.

3

Every recommendation is immutable and reproducible.

Snapshot + model versions + weights + scores + action + outcome — persisted forever. A regulator can audit any decision five years later. This is not optional.

4

Outcome (40%) outweighs Cost (25%) in the scoring.

If you swap those weights — even slightly — you've built a different system. The whole program's value depends on not optimizing cost at the expense of claimant outcomes. (Regulator complaint ratios are the early warning.)

5

Ship Phase 1 with rules + simple classifier + scorecard MVP. Resist building the learning loop first.

C4 only makes sense once C1/C2/C3 are producing recommendations and capturing outcomes at scale. Building C4 first is the classic ML-platform trap. Don't fall in.
